# 组件规范与状态矩阵（前端可直接照此实现）

> 所有状态对应可渲染的 DOM 结构见 `prototype.html`；本文件补充**何时出现、文案、禁用规则、不可做的事**。
> 状态值一律使用后端枚举（需求 7.1），前端**不做二次推导，不从中文日志猜状态**。

## 0. 全局约束

1. 任何“禁用”必须同时给出原因文案（按钮下方 hint、title 或页面提示条），不允许静默置灰。
2. 状态同时用中文与颜色表达；颜色不得是唯一区分手段。
3. 不允许出现“强制通过”“任意跳步”“修改历史结论”“强制解锁”入口。
4. 数字使用等宽数字；时间显示到时/分/秒，时区由后端事件时间决定并在报告中标注。
5. 前端只消费事件与快照；进程、机器锁、清理判断不以前端状态为准。

## 1. 运行配置表单（WEB-01）

| 字段 | 控件 | 必填条件 | 校验与提示 |
| --- | --- | --- | --- |
| 被测程序 EXE 路径 | 文本（mono） | 始终必填 | 非空且以 `.exe` 结尾 |
| 配方目录 | 文本（mono） | 非空校验由后端准备检查给出 | 前端只做空值提示，存在性由 `/api/config` 校验 |
| 证据目录 | 文本（mono） | 始终必填 | 空值阻断开始 |
| 预期版本号 | 文本（mono） | **未勾选“跳过版本断言”时必填** | 勾选后必填星号消失、错误清除、不阻止启动 |
| 预期编译日期 | 文本 `yyyy-MM-dd` | 同上 | 格式校验；不从被测 EXE 自身生成 |
| 登录密码 | 不提供输入框 | — | 显示“已配置/未配置”；已配置时只给状态，不回传、不回显 |

状态：

- `初始`：加载本机已保存配置，右上角“已加载本机配置”。
- `编辑`：输入即时保存草稿（防误刷新丢失），显式“保存配置”后写入本机配置并 toast。
- `校验错误`：字段下方红字 + 边框转红；开始按钮可置灰但原因必须写清。
- `运行中只读`：全部控件禁用，右上角“运行中只读（本轮快照）”；显示本轮快照区（runId、选项快照、开始时间）。
- `保存成功`：右上角“已保存 · HH:mm:ss”。

不可做：在运行中修改本轮配置（只能影响下一轮）；把密码显示为 `******` 假装可编辑。

## 2. 三个运行选项（WEB-10）

结构：三项复选，逐项一行：标题 + 一句后果说明。默认**三项全不选**。

| 交互 | 行为 |
| --- | --- |
| 勾选“跳过硬件步骤” | 自动取消“人工执行硬件步骤”；`hw=skip` |
| 勾选“人工执行硬件步骤” | 自动取消“跳过硬件步骤”；`hw=manual` |
| 取消当前硬件项 | 回到两项都不选；`hw=strict`（允许，不设必选校验） |
| 勾选/取消“跳过版本断言” | 独立布尔，不影响硬件项 |
| 开始后 | 三项只读展示，并显示快照（页面、报告、历史三处一致） |

文案（策略条，随选择即时变化）：

- 全不选：**严格执行**：版本号与编译日期核验、硬件操作与断言全部按原步骤执行。
- 仅版本：**跳过版本断言**：01.02 记为跳过；版本号与编译日期的缺失不阻塞启动，硬件仍严格执行。
- 仅跳过硬件：**跳过硬件步骤**：版本号与编译日期照常核验；整步硬件记为跳过，混合步骤保留软件断言结果。
- 版本 + 跳过硬件：两者组合，01.02 跳过；硬件步骤跳过，混合步骤保留软件断言。
- 仅人工：**人工执行硬件步骤**：版本核验照常；硬件操作点等待网页确认后继续，仍执行软件断言。
- 版本 + 人工：01.02 跳过；硬件操作点等待网页确认后继续。

服务端返回硬件双选时：页面显示明确错误（不创建运行、不启动进程），不复用前一次运行。

## 3. 按钮

| 类型 | 样式 | 用法 |
| --- | --- | --- |
| 主操作 | 蓝底白字 40px | 仅“开始执行”；确认卡内“完成（现场已操作）” |
| 次操作 | 白底描边 34/28px | 保存配置、重新检查、查看报告、历史 |
| 危险 | 白底红字描边 | “判定失败”（确认卡内），不使用红底实心（避免误触成主操作） |
| 警示 | 白底橙字描边 | “报告阻塞” |
| 幽灵 | 无描边 | 关闭、返回、演示控件 |

禁用规则：

- “开始执行”：`配置校验失败` / `本机忙` / `待现场处理` / `运行中` 任一成立即禁用，并在按钮下写原因。
- “完成/阻塞/失败”：仅在存在**当前等待确认点**时可用；提交后立即禁用（幂等）。
- 提交中：按钮进入 `aria-busy`，保留宽度，防止重复点击。

## 4. 状态徽标

固定 22px 高、全圆角、6px 圆点 + 文字。文字集合（不可改写、不可只用颜色）：

`未执行` / `执行中` / `等待人工确认` / `成功` / `成功·人工确认` / `跳过·部分硬件` / `跳过·整步硬件` / `跳过·明确要求` / `阻塞` / `失败` / `中断·结果未知`。

“执行中”带 8px 环形旋转；其余为实心圆点。“等待人工确认”旁允许显示已等待时长。

## 5. 阶段步进（WEB-08）

阶段：`准备 → 执行 → 等待人工 → 清理 → 结束`。

- 已完成：绿底勾号；当前：蓝底序号；待现场处理：第 4 段替换为“待现场处理”并使用橙底。
- 阶段与步骤结果**分开**：清理进行中时步骤仍显示各自终态。
- 阶段不随页面刷新回退（以后端 stage 为准）。

## 6. 汇总与计数（WEB-09）

- 主计数五项固定顺序：成功 / 跳过 / 阻塞 / 失败 / 未执行；每步只计一次。
- “等待人工”和“中断·结果未知”**单独**以徽标展示，不并入未执行；所以可能出现 `成功+跳过+阻塞+失败+未执行+等待+中断 = 27`。
- 进度分母固定本期 27；文案固定为“已收敛步骤（分母为本期 27 步，不是 184 步）”。
- 范围说明常驻：`本期已实现 01—06 节 27 步；完整设计 184 步，其余 157 步未实现。本页结论不代表整条实机主流程通过。`
- 汇总中的“清理”只显示清理状态，不合并到步骤结论里。

## 7. 步骤清单（WEB-03 / WEB-04）

列：`stepId(70px) | 名称+标签+原因(1fr) | 状态(132px) | 耗时(82px)`。

行状态：

| 行状态 | 视觉 | 说明 |
| --- | --- | --- |
| 普通 | 白底、下边框 | — |
| 当前执行/等待 | 浅蓝底 + 左侧 3px 蓝条 | `aria-current="step"` |
| 失败 | 极浅红底 + 左红条 | 行内保留原始原因 |
| 阻塞 | 极浅橙底 + 左橙条 | 原因必须可见 |
| 选中 | 浅蓝底（可叠加） | 显示右侧详情 |

- 步骤名后允许标签：`原用例人工点`（03.01）、`登录后执行`（01.02，说明真实事件顺序与编号顺序不同）、`含硬件部分`（详情内）。
- 原因显示在名称下一行，11px；无原因不占位（不写“—”）。
- 01.02 可能出现“编号 01.02 晚于 02.01 显示结果”的情况：清单按编号排序，状态按事件更新，**不得为对齐编号而改写顺序或延迟渲染**。
- 未开始的步骤保持“未执行”；失败/阻塞后其余步骤**不得**批量改成跳过/成功。
- 键盘：行可 Tab 聚焦，Enter/Space 选中。

## 8. 人工确认卡（WEB-05）

出现条件：`waiting` 状态且存在 `checkpointId`。

必含：步骤编号 + 名称、确认点 ID、等待起点、已等待时长（每秒刷新）、现场操作说明（有序列表）、备注输入、“完成 / 报告阻塞 / 判定失败”、幂等与过期说明。

规则：

- 卡在步骤清单**上方**，不覆盖清单；不用模态，保证日志仍可查看。
- “完成”仅代表现场已操作，随后仍执行软件断言；不得写成“通过”。
- 阻塞/失败必须填写备注（原因），未填时在字段下红字提示且不发请求。
- 提交按钮状态：`可提交 → 提交中 → 已提交（禁用）`；重复提交同一 `checkpointId + requestId` 幂等，返回同一结果。
- 旧页面/超时/已结束确认点提交：页面显示“该确认点已失效，未改变结果”，并刷新快照；不重试、不继续步骤。
- 刷新/重连：恢复到同一确认点，计时基于 `startedAt` 计算，不重置。
- 跳过硬件策略下**不出现**被跳过步骤的确认点。

## 9. 待现场处理卡（WEB-08）

出现条件：`stage=pending_field`（硬件状态未确认）。

必含：

- 醒目说明：不自动结束被测程序、占用未释放、禁止新一轮、无强制解锁入口。
- runId、阻塞步骤、原始结论（阻塞/失败，现场处理完成后**不改写**）、被测进程（名称+PID）。
- 现场处理规程 4 步。
- 核验项 3 条（进程已退出 / 无冲突进程 / 设备状态确认），状态由执行器返回：`待核验 / 已核验`。
- “重新核验现场状态”按钮；“提交现场处理完成”按钮在核验通过前禁用并说明原因。
- 现场处理记录文本框（处理人/时间/现状），随报告保存。

不可做：用前端勾选框代替执行器核验；把“提交”当成强制解锁；清理失败时仍显示“本轮全部成功”。

## 10. 日志查看（WEB-06）

- 深色日志块（唯一深色区域，表示“机器输出”），等宽 11.5px，`时间 | 级别 | 内容` 三列。
- 级别仅 INFO/WARN/ERR；ERR 用于记录失败原因，但**失败结论以状态事件为准**。
- 只读、可滚动、不自动滚到底（用户可能正在回看）；提供“本步日志 N 条”。
- 页脚注明“只展示结构化事件与本步日志，不解析中文日志推断状态”。
- 不显示登录密码；后端脱敏，前端不做解密或猜测。

## 11. 证据（WEB-06）

- 2 列卡片：缩略图/类型图标 + 文件名（省略号）+ 类型与大小。
- 点击通过 `GET /api/runs/{runId}/artifacts/{artifactId}` 获取；**不拼本地路径**。
- 三种态：`可预览`（图片/JSON/文本）、`格式不支持`（明确说明，给下载）、`缺失`（虚线卡 + “文件已被移动或删除；不据此改写原运行结论”）。
- 证据索引属于历史记录，历史详情中同样可查看，但只读。

## 12. 连接状态与恢复（WEB-07）

| 状态 | 展示 |
| --- | --- |
| 正常 | 顶栏绿点“状态通道正常” |
| 中断 | 顶栏橙徽标“状态连接中断”；页面顶部提示条：执行器可能仍在运行，连接失败不等于测试失败 |
| 补齐中 | 蓝徽标“正在补齐事件…”；文案说明按 runId + sequence 去重 |
| 恢复完成 | toast：快照已恢复、补齐 N 条事件、未重复执行步骤 |

约束：恢复期间不刷新整页、不清空已显示状态；重复事件按 `sequence` 丢弃；**连接状态与运行结论互不影响**。

## 13. 历史运行（WEB-12）

- 表格列：runId / 开始时间 / 执行策略 / 结论 / 清理 / 成功·跳过·阻塞·失败·未执行。
- 结论徽标：通过（绿）/ 未通过（红）/ 待现场处理（橙）。
- 行为：整行可点击；进入详情后顶部固定“历史记录 · 只读”横幅，展示 runId，无任何确认/执行按钮。
- 详情包含：结论摘要、计数、配置快照（版本/编译日期，不含密码）、证据目录、步骤结果、报告入口。
- 空态：`暂无历史运行。完成至少一轮后在此查询。`
- 证据缺失：在证据卡片显示缺失，不改写结论。

## 14. 提示条 / Toast / 弹层

| 元素 | 用途 | 规则 |
| --- | --- | --- |
| 提示条 banner | 连接状态、范围说明、待现场处理说明、历史只读 | 常驻，直至状态改变；不使用自动消失 |
| Toast | 保存成功、请求被拒、确认已提交、恢复完成 | 3.6s 自动消失；错误用深红底；不承载唯一关键信息 |
| 弹层 | 证据预览、完整报告 | 720px 宽、Esc/遮罩关闭、焦点可返回触发元素；只读 |

## 16. 与接口草案的字段映射（契约草案，待后端确认）

接口草案来自可研评论（司小懿提出、待卫青确认，见任务评论）。本设计只**按字段消费**，不改契约：

| UI 位置 | 字段（建议） |
| --- | --- |
| 配置表单 | `GET/PUT /api/config`：`exePath / recipeDir / evidenceDir / expectedVersion / buildDate / passwordConfigured / options` |
| 选项 | `POST /api/runs`：`skipVersionAssertion:boolean`、`hardwarePolicy: strict \| skip \| manual` |
| 阶段/计数 | `GET /api/runs/current`：`stage / counts / cleanup / pendingField / optionsSnapshot` |
| 步骤 | 快照 `steps[]`：`stepId / name / section / status / reason / startedAt / durationMs / manual / hardwareSkipped` |
| 事件流 | `GET /api/runs/{runId}/events?after=seq`：`protocolVersion / runId / sequence / at / type / stepId / phase / result / reason / artifactIds` |
| 确认 | `POST /api/runs/{runId}/checkpoints/{checkpointId}/confirm`：`requestId, result(done\|blocked\|failed), reason` |
| 证据 | `GET /api/runs/{runId}/artifacts/{artifactId}` |
| 历史/报告 | `GET /api/runs`、`GET /api/runs/{runId}/report` |

前端需向后端确认的三点（属草案范围，不在本设计内决定）：

1. `hardwarePolicy` 枚举名与“两项均不选”的严格语义映射是否一致（草案建议 `strict`）。
2. 事件 `type` 的完整列表是否覆盖“待现场处理 / 现场处理确认 / 占用解除”。
3. 快照中的 `counts` 是否已排除 `waiting` 与 `unknown`（本设计按“单独展示、不并入未执行”绘制）。
